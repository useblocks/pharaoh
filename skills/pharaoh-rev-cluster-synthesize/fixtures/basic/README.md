# basic

Three lower `comp_req` needs (`CREQ_csv_validate_headers`, `CREQ_csv_map_columns`, `CREQ_csv_write_rows`) already exist for a CSV Exporter component but share no upper-rung `feat` anchor. `input-cluster.json` provides the precomputed cluster (`cluster_id: cluster_csv_export`) with the three member ids and their full resolved need objects (`type`, `title`, `status`, `content`, existing `satisfies`, `file`, `line`), standing in for what `ubc build needs --format json` would return for those ids (Tier 1 of `shared/data-access.md`). Each member starts with an empty `satisfies`.

`input-intent.json` supplies two intent snippets: a commit message and a PR description, both naming "CSV export" explicitly. Both snippets ground the same theme the three members compose, so both qualify as `intent_refs`.

This fixture models the synthesis rung of a reverse-recovery plan, which invokes this skill with `status: "recovered"` (see `pharaoh-write-plan/templates/reverse-recover-rung.yaml.j2`'s `cluster_synth_*` task, mirroring the extraction rung's `pharaoh-req-from-code` call) -- not the skill's own bare default (`"draft"`, for a direct, non-reverse-recovery invocation).

Expected: one synthesized `feat` need (`FEAT_csv_export`) whose body covers all three member behaviors (header validation, column mapping, row writing), whose `raw_rst` carries `:status: recovered` and no down-link to the members, whose `intent_refs` cites both intent snippet ids, and whose `intent_gap` is `false` since the intent signal grounds the rung.

`member_updates` lists exactly the three member ids. Each entry's `raw_rst` is that member's own directive block, re-rendered with `satisfies` extended to `["FEAT_csv_export"]` (each member had no prior `satisfies` value in this scenario) and every other pre-existing field (`id`, `type`, `title`, `status`, content) unchanged. `file` / `line` echo the member's resolved directive location from `input-cluster.json`. This skill authors these RST edits itself -- `pharaoh-rev-record-ledger` never sees `member_updates` and never applies an up-link. The plan persists these edits the same way it persists `reqs[0].raw_rst`. This is the fixture's happy path -- a cluster with a coherent shared theme and intent signal that actually names it, as opposed to a cluster requiring an `intent_gap: true` result.
